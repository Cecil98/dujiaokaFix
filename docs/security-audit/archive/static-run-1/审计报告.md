## 1. 结论摘要

本次审计对 `upgrade/php83` 分支（PHP 8.3 + Laravel 12 升级）做了完整的静态审计：框架、依赖、路由与鉴权、危险函数、安全配置、支付/业务逻辑、并发、上传与供应链。**未发现可直接利用的未认证 RCE**，也未发现已知 CVE 命中的依赖。

风险集中在四类：

1. **支付回调信任链**（高危）：易支付回调签名把「公开占位密钥」当作密钥来源，匿名者可离线算出签名并完成订单取走卡密（PQ-01）；Stripe 的 `check` 把期望金额与订单绑定令牌都交由客户端决定（PQ-05）。
2. **数据暴露**（高危）：匿名按邮箱检索订单直接返回卡密明文，无归属校验、无限流（PQ-04）。
3. **安装器与配置前提**（中危）：`install.lock` 缺失时匿名安装器可导入破坏性 SQL 并重置管理员（PQ-03），还可把 DB/Redis 目标指向任意主机做内网探测（PQ-03-SSRF）。
4. **并发与完整性**（中危/低危）：优惠券计数、卡密分配、订单过期、库存扣减均为「先查后写」且缺少行锁/唯一约束（PQ-06-A/B/C、PQ-02）。

另有若干**加固类**问题（Secure Cookie 默认关闭、改密不吊销会话、管理员可上传任意扩展名到 Web 根、管理员可配置出站 URL）评为低危，但仍建议在发布前一并处理。

> 重要前置说明：本报告全部结论为**源码级确认**，除依赖审计（`composer audit`）与版本核对为工具实测外，**未发送任何 HTTP 请求、未启动应用容器、未执行漏洞利用 PoC**。凡涉及运行时行为（Stripe 账户交互、并发竞态统计、错误分支 oracle）的判定，均以源码路径 + 框架/DB 语义推导，并在对应条目中标注。

## 3. 已确认发现

> 严重性采用验证器最终裁定（部分条目相对初筛已下调，理由见各项“偏差说明”）。编号与既有 `raw/priority-queue.json` 一致，便于追溯。

### 3.1 高危

#### PQ-01 · 易支付回调使用公开占位密钥，匿名可伪造通知完成订单并取走卡密

- **位置**：`app/Http/Controllers/Pay/YipayController.php:94`
- **CWE**：CWE-798（硬编码/占位凭据）、CWE-345（验证不足）
- **可达性**：匿名；GET `/pay/yipay/notify_url`
- **置信度**：0.80

**链路**

1. `routes/common/pay.php:28` 注册 `GET pay/yipay/notify_url`，所属组仅 `dujiaoka.pay_gate_way`，而该中间件是纯直通（`app/Http/Middleware/PayGateWay.php:17-20`）。GET 天然不受 CSRF 约束，且 `pay/*/notify_url` 还在 `VerifyCsrfToken.php:24` 豁免列表内。
2. 签名算法为 `md5(排序后的参数串 + $payGateway->merchant_pem)`（`YipayController.php:94`），校验用 `hash_equals`（:95）——算法与比较本身无缺陷。
3. **缺陷在密钥来源**：`database/sql/install.sql:515-517` 把易支付行的 `merchant_pem` 写成公开占位字面量；`:538-540` 又执行「全部 `is_open=0`，仅 `/pay/yipay` 置 1」，因此**全新安装默认唯一启用的渠道正是签名可离线计算的这个**。`App\Casts\EncryptedOrPlaintext` 对未加密值原样返回，占位符被直接当作签名密钥。
4. 下单时 `payway` 被当作 `pays.id` 直接落库，未校验渠道存在/启用/已配置（`Home/OrderController.php:75` → `OrderProcessService.php:329`）。
5. 签名通过后调用 `completedOrder(out_trade_no, money, trade_no)`（:101），金额校验为 `bccomp($order->actual_price, $actualPrice, 2)`（`OrderProcessService.php:418-422`），而 `money` 取自攻击者已知的订单页金额，等于自证。
6. `processAuto()` 把卡密写入 `orders.info`（`OrderProcessService.php:520-524`），该字段可在未认证的订单详情页读取（`Home/OrderController.php:171-179`）。

**影响**：零支付完成任意自有订单，按单榨取库存卡密。

**偏差说明**：初筛称“需 `install.lock` 存在”，实际支付路由未挂 `dujiaoka.boot`，该前提不成立（不影响结论）。若运营者已把 `merchant_pem` 换成真实密钥则不可伪造，故置信度 0.80 而非更高。

**修复建议**

- 回调前拒绝空密钥或已知占位符的渠道；
- 用易支付**服务端查询接口**二次核对交易状态与金额，回调仅作触发；
- 为回调绑定服务端 nonce（可复用 `buildOrderContextToken` 思路）；
- `install.sql` 出厂全部渠道 `is_open=0`，且不写任何可用凭据字面量；
- 下单时校验 `pay_id` 存在、启用、已配置、对该客户端可见；
- 增加回归测试：占位符渠道不得完成订单。

#### PQ-04 · 匿名按邮箱检索订单直接返回卡密明文

- **位置**：`app/Http/Controllers/Home/OrderController.php:206`
- **CWE**：CWE-359（隐私暴露）、CWE-200（信息泄露）
- **可达性**：匿名；`POST /search-order-by-email`
- **置信度**：0.90

**链路**

1. `routes/common/web.php:32` 在 `dujiaoka.boot` 组内，无 `auth`、无 `throttle`（`app/Http/Kernel.php:34-43` 的 `web` 组不含限流，限流只在 `api` 组）。
2. 控制器（:208-216）仅在 `is_open_search_pwd == OPEN` 时要求 `search_pwd`；而该配置项**默认不存在**，`app/Helpers/functions.php:58-62` 回落到 `BaseModel::STATUS_CLOSE = 0`，分支被跳过。
3. `OrderService::withEmailAndPassword`（:259-269）退化为 `where('email', ?)->orderBy('created_at','DESC')->take(5)->get()`，**无任何归属谓词**；下单时写入的 `dujiaoka_orders` Cookie 从未被查询。
4. 结果渲染 `static_pages/orderinfo`（:221），三个主题模板均直接输出 `$order['info']`（unicorn:83-85 / hyper:97-98 / luna:112-114），而该字段即卡密明文（`OrderProcessService.php:520-524`，且卡密此时已被标记售出）。

**影响**：泄露任意邮箱最近 5 笔订单的卡密、订单号、金额、时间。DB 存在 email 索引，可低成本批量扫库；卡密已售，受害者无补救。

**偏差说明（修正初筛）**：

- 订单详情**未渲染买家 IP**（模板中无 `buy_ip`），初筛的该影响不成立；
- 单次请求上限 5 条，非全量导出。

**修复建议**

- 以归属证明替代邮箱匹配（一次性邮件令牌 / 订单号 + 非空 `search_pwd`）；
- `is_open_search_pwd` 默认开启，下单时强制写入非空口令，并用 `hash_equals` 比对哈希；
- 列表视图掩码卡密，仅在通过归属校验的详情页展示；
- 对搜索类路由加 `throttle:10,1`，统一“未找到”响应以抗枚举。

#### PQ-05 · Stripe `check` 订单绑定令牌可选，且以订单原价完成订单

- **位置**：`app/Http/Controllers/Pay/StripeController.php:485`
- **CWE**：CWE-472（外部可控的假定不可变参数）、CWE-840（业务逻辑）
- **可达性**：匿名；`GET /pay/stripe/check`
- **置信度**：0.82

**链路**

1. `routes/common/pay.php:37` 注册 `GET stripe/check`；GET 无 CSRF，`dujiaoka.pay_gate_way` 直通。
2. 期望金额取自请求：`$stripeUsdAmount = (int) $request->input('stripe_usd_amount', <服务端计算>)`（:485-488），客户端值优先。
3. 订单绑定令牌只在客户端主动提交时校验：`if ($request->filled('context') && !$this->validateOrderContextToken(...))`（:489-494）——不传 `context` 即跳过。
4. Source 校验（:501-508）对比的也是客户端提供的 `stripe_usd_amount` 与客户端设置的 `owner.name`（下单页 JS 中用公开 pk 创建 Source），两侧都受攻击者控制。
5. 完成后调用 `completedOrder($orderid, $cacheord->actual_price, $charge->id)`（:515），而 `completedOrder` 又用同一 `actual_price` 做 `bccomp`（`OrderProcessService.php:418-422`），比较恒为 0，**实付金额从未被验证**。
6. 同文件 `returnUrl()`（:454-459，服务端计算并比对金额/币种）与 `charge()`（:544-548）写法正确，证明安全实现已知但 `check()` 未采用。

**前提**：Stripe 渠道被运营者启用（默认 `is_open=0`）且配置真实 pk/sk；Stripe 存在各币种最低收款额（USD 约 0.50）。

**影响**：以最小额 Source 完成高价订单并自动发卡，造成直接资金损失。

**修复建议**

- `context` 改为**无条件**校验；确需无令牌入口时用独立签名的 nonce 重定向 URL；
- 删除客户端 `stripe_usd_amount` 的权威地位，期望金额一律服务端计算；
- `Charge::create` 后断言 `amount`/`currency`，并把**实际结算金额**传入完成流程；
- Source 与订单服务端绑定（持久化 `source_id` 或校验 `metadata`）；
- 加订单状态前置检查与路由限流。

### 3.2 中危

#### PQ-03 · 匿名安装器可导入破坏性 SQL 并重置管理员

- **位置**：`app/Http/Controllers/Home/HomeController.php:202`
- **CWE**：CWE-306（关键功能缺失认证）、CWE-284
- **可达性**：匿名；`GET /install` + `POST /do-install`
- **置信度**：0.74

**链路**：`routes/common/web.php:37-42` 仅挂 `install.check`；`InstallCheck.php:19-23` 只判断 `base_path()/install.lock` 是否存在。`doInstall()` 依次执行 `file_put_contents(.env)`（:202）→ `DB::unprepared(file_get_contents(install.sql))`（:204，含 21 条 `DROP TABLE IF EXISTS`）→ 覆盖 `admin_users` id=1（:206-215）→ 最后才写 `install.lock`（:216）。CSRF 不构成防护：`GET /install` 会把同一会话的令牌发给匿名访问者。

**两处对初筛的修正（导致 medium 而非 high）**：

1. 初筛称「.env 写失败时 SQL 导入与 admin 重置仍执行」——**不成立**。Laravel 12 的 `HandleExceptions` 将 `error_reporting(-1)` 且把 `E_WARNING` 转为 `ErrorException`；`file_put_contents` 位于 try 块内，异常被 `:224` 的 `catch` 捕获后直接返回「安装失败」，到不了 `:204`。默认镜像 `/app` 为 root 所有 0644，反而阻断了破坏链。
2. 初筛遗漏关键前提：DB/Redis 主机**取自请求**（:161-175），会覆盖既有配置且无回落。要破坏目标库需已知目标 MySQL 凭据；若指向攻击者自建库，则 DROP/UPDATE 只作用于其自己的实例。

**残余风险**：安装器「仅凭文件是否存在」开放，本身就是缺陷；原生 PHP-FPM 部署文档未要求创建 `install.lock`，且该锁一旦被删/卷重挂即重新暴露。

**修复建议**：仅当 `INSTALL=true` 或 CLI 开关开启时暴露安装路由；以 `fopen($lock,'x')` 原子建锁作为**第一个动作**，失败即中止；`.env` 写失败要显式报错且不继续；DB/Redis 目标不从请求读取，或要求安装令牌 + `filter_var` 拒绝私网；用增量迁移替代 `DROP TABLE`；种子不写死 admin 行。

#### PQ-03-SSRF · 安装器以请求指定的 DB/Redis 主机发起连接

- **位置**：`app/Http/Controllers/Home/HomeController.php:181`
- **CWE**：CWE-918（SSRF）
- **置信度**：0.80

`db_host/db_port/redis_host/redis_port/redis_password` 经 CRLF 过滤后逐字合并进 `config('database.connections.mysql')` 与 `config('database.redis.default')`（:161-176），随后 `DB::connection()->select('select 1 limit 1')`（:179）与 `Redis::set/get`（:181-182）真实拨号。`HomeController.php:147-158` 只校验 `admin_*`、`app_url`、`admin_path`，**未校验任何 host**。

已逐条排除的反驳：

- `DatabaseManager::purge(null)` 不会移除 `'mysql'` 连接键，但重连闭包会重新读取当前配置并拨号攻击者主机（已核对 vendor `DatabaseManager.php` / `ConnectionFactory.php`）；
- `RedisServiceProvider` 在解析时对配置做快照，bootstrap 阶段尚未使用 Redis（`SESSION_DRIVER=file`），因此被篡改的 host 会被采用；
- `redis_password=` 经 `ConvertEmptyStringsToNull` 变为 `null`，`PhpRedisConnector` 的 `AUTH` 仅在密码非空时发送，故对无密码内网 Redis 的盲写成立。

**影响**：内网 MySQL/Redis 服务枚举（三档错误分支构成 oracle：Redis 配置错误 / 数据库配置错误 / 安装失败），以及对无密码 Redis 的盲写（固定键值）。不返回内网响应体，故 medium。

**修复建议**：服务端校验 host（`FILTER_VALIDATE_IP`/`FILTER_VALIDATE_DOMAIN`，解析后拒绝回环、私网、链路本地、CGNAT、ULA），端口白名单；优先从 `.env` 读取目标；安装接口要求认证或一次性令牌；返回统一失败文案（细节只进日志）。

#### PQ-06-A · 优惠券剩余次数先查后减（TOCTOU），可并发超发折扣

- **位置**：`app/Service/OrderService.php:165`
- **CWE**：CWE-362（竞态）、CWE-367（TOCTOU）
- **可达性**：匿名；`POST /create-order`
- **置信度**：0.85

`validatorCoupon()` 只做只读判断 `if ($coupon->ret <= 0) throw`（:165），`CouponService::withHasGoods()` 是普通 `first()`（:29-35，无 `lockForUpdate`/`sharedLock`）；真正扣减在 `CouponService::retDecr()` 的 `decrement('ret', 1)`（:58-63），**既无 `where('ret','>',0)` 也不检查影响行数**。InnoDB REPEATABLE READ 下检查是快照读、UPDATE 是当前读，所有通过过期检查的事务都会各扣一次，`ret` 可被打到负数（字段是有符号 int，无 CHECK）。

折扣被持久化（`OrderProcessService.php:339、348-352`）并成为实际支付金额；`CouponBack` 在订单过期时回补一次（`Jobs/CouponBack.php:47-55`，默认 5 分钟过期），因此该竞态可**周期性重复利用**。

**放大路径**：当折扣 ≥ 商品价时，`actual_price` 被夹到 0，`PayController.php:188-196` 会以 `FREE-<sn>` 直接完成订单 —— 免费数字商品。该分支需特定券配置，故不据此上调整体评级。

**限制**：串行攻击者在 `ret=0` 处被拦（`PQ-06-R1` 已排除串行复用）；需并发命中事务窗口（毫秒级）+ 已知券码。

**修复建议**：改为原子条件扣减 `where('ret','>',0)->decrement('ret',1)` 并断言影响行数，0 则抛异常触发 `DB::rollBack`；或在 `withHasGoods` 中 `lockForUpdate`；启用 `is_use` 判定；`ret` 用 `GREATEST` 或 DB CHECK 兜底；下单路由加限流并默认开启验证码。

#### PQ-06-B · 卡密分配先读后写，可将同一张卡发给两个订单

- **位置**：`app/Service/CarmisService.php:29`
- **CWE**：CWE-362、CWE-367
- **置信度**：0.82

读侧 `withGoodsByAmountAndStatusUnsold()` 为 `where(status=UNSOLD)->take($byAmount)->get()`（:29-37），**无 `orderBy`、无 `lockForUpdate`**；写侧 `soldByIDS()` 为 `whereIn('id',$ids)->where('is_loop',0)->update(status=SOLD)`（:49-52），**缺 `status=UNSOLD` 的 CAS 谓词**且忽略影响行数。

两个并发事务（不同订单、同一商品）快照读到同一批未售卡密，`OrderProcessService.php:514` 的数量检查在各自快照上都通过，随后同一卡密文本被写入两个已支付订单（:522-524）并分别邮寄（:542）。第二个 UPDATE 在锁等待后重新求值 `id IN (...) AND is_loop=0` 仍为真，MySQL 报告 0 changed rows、不抛异常，事务正常提交 —— 状态静默不一致，运营无告警。

**附带缺陷**：读侧未过滤 `is_loop=0`，而写侧过滤了，导致 loop 卡可满足数量检查却永不被标记售出。

**前提比初筛更宽松**：自动发货商品库存取 `withCount(carmis where status=UNSOLD)`，下单只校验 `by_amount > in_stock` 且**不预留**，因此仅 1 张未售卡也能产生两个金额为 1 的订单并分别支付。

**影响**：同一付费数字商品被重复交付 + 静默数据不一致；攻击者需实付两单，无越权或直接牟利，故 medium。

**修复建议**：在完成事务内 `orderBy('id')->limit($n)->lockForUpdate()->get()`；或 CAS 更新并断言影响行数等于 N，不等则抛异常回滚为 `STATUS_ABNORMAL`；读侧补齐 `is_loop=0`；可选以 goods 行为序列化点（`lockForUpdate` 或 `Cache::lock`）。

#### PQ-02 · 订单完成/过期缺少行锁与唯一约束

- **位置**：`app/Service/OrderProcessService.php:395`｜CWE-362 / CWE-367｜置信度 0.72

`completedOrder()` 在事务内用普通 `first()` 读订单（`OrderService.php:212-216`），无 `lockForUpdate`、无条件 UPDATE；`orders.trade_no` **无唯一索引**（`install.sql:444-472`），故 :411-417 的存在性检查只是建议性的。`Jobs/OrderExpired.php:53-59` 把 `status==WAIT_PAY` 检查与 `expiredOrderSN()`（`OrderService.php:228-231`，**仅按 order_sn 无条件 update**）分离。InnoDB 快照读下，过期任务可把已支付订单改为 `STATUS_EXPIRED` 并回退优惠券。

#### PQ-07 · `goods.api_hook` 无校验传入 `file_get_contents()`

- **位置**：`app/Jobs/ApiHook.php:85`｜CWE-918｜置信度 0.72

#### PQ-08-F1 · Session Cookie 默认不带 `Secure`

- **位置**：`config/session.php:169`｜CWE-614 / CWE-1188｜置信度 0.68

`.env.example:69` 出厂写死 `SESSION_SECURE_COOKIE=false`，`Env::getOption()` 将其转为布尔 `false`，`StartSession` 用该值构造 Cookie；因 `false` 非 `null`，Symfony 的 `secureDefault` 自动标记无法覆盖，`Set-Cookie` 永不带 `secure`。安装器会逐字复制 `.env.example`，故默认安装均继承该值。`HttpOnly` 与 `SameSite=Lax` 均已开启。

**对初筛的修正**：初筛称「Laravel 永不触达 Symfony HTTPS 自动加 Secure 路径（`Response::prepare` 是死代码）」——**证伪**。`Router::runRoute()`（`Router.php:799`）会调用 `prepareResponse()`，最终执行 `$response->prepare($request)`（:946），因此正确修复是恢复 `null` 自动检测，而**不是**硬编码 `true`（仓库参考部署为纯 HTTP，硬编码 true 会直接破坏登录）。

**修复建议**：`'secure' => env('SESSION_SECURE_COOKIE')`；移除 `.env.example` 的 `false` 并加注释；代理终止 TLS 时说明需配 `TRUSTED_PROXIES`；边缘加 301 + HSTS；加回归测试断言 HTTPS 请求 `Set-Cookie` 含 `secure`。

#### PQ-08-F2 · 管理员改密不吊销其它会话

- **位置**：`app/Http/Kernel.php:38`｜CWE-613｜置信度 0.72

`AuthenticateSession` 在 `web` 组被注释，且从未为 `admin` guard 注册（`grep vendor/dcat` 无匹配；`:87` 仅为优先级列表）；`app/Admin/Controllers/AuthController.php:46-76` 的改密路径只写 bcrypt 哈希，无 `logoutOtherDevices`、无 `cycleRememberToken`、无跨会话失效。已存在的管理员会话在改密后继续通过仅检查 `guest()` 的 admin 中间件（vendor `Authenticate.php:19-29`），可长期存活（120 分钟滑动过期）。

**对初筛的修正**：「remember cookie 可维持 576000 分钟持久控制」——**证伪**。Laravel 12.70.1 的 recaller 第三段是密码哈希的 HMAC（`SessionGuard.php:224-241`），改密后旧 remember cookie 自动失效。

**修复建议**：为 `admin_users` 增加 `session_version`/`password_changed_at`，改密时同事务递增，并在 admin 中间件校验不符即登出 + `invalidate()` + `regenerateToken()`；登录时写入版本号；勿仅依赖 `AuthenticateSession`（其绑定默认 `web` guard）。

#### PQ-06-C · 库存在下单时校验、支付时才无守卫扣减

- **位置**：`app/Service/GoodsService.php:131`｜CWE-840 / CWE-362｜置信度 0.78

下单仅比较 `by_amount > goods.in_stock`（`OrderService.php:114`），**从不扣减也不预留**；支付后 `processManual` 调 `inStockDecr()` → `decrement('in_stock',$number)`（:131-134），**无 `where('in_stock','>=',$n)` 且忽略返回值**，字段为有符号 int 无 CHECK（`install.sql:375`），可被压成负数。无需并发即可触发（先建两单，再分别支付）。

**影响边界**：每负一单位需实付商品全价，故为库存完整性/超卖与低价刷单 DoS，而非牟利原语；自动发货商品不调用该扣减，不受影响。与 PQ-06-A 组合可放大（券把 `actual_price` 归零 → 免费扣库存）。

**修复建议**：下单时条件更新预留库存并在过期任务中释放；支付时同样条件扣减；DB 加 `CHECK(in_stock >= 0)` 或 `unsigned` 并写入 `upgrade-php83.sql`；对 0 元完成加限流。

- **SAST**：未运行 Semrush/`semgrep`、`phpstan`/`psalm` 安全规则集、`progpilot`、`SonarQube`。

- **容器/镜像扫描**：未运行 Trivy、Grype、Snyk Container、Docker Scout；未扫描基础镜像 `webdevops/php-nginx:8.3` 的 OS 包漏洞。

### 6.3 范围内的已知盲点

- **`vendor/` 未做 AST sink 扫描**（`sink_finder.php` 的 `collectPhpFiles()` 跳过 vendor），dcat/laravel-admin 与其它 Composer 包仅做人工重点阅读（上传、权限、ignition、payjs、SessionGuard/Cookie/DatabaseManager/Redis 连接器），**非全量**。
- **fork 与上游 diff 未执行**（见“已接受风险”1）。
- **Blade/`{!! !!}` XSS sink 未被工具建模**：`sink_finder.php` 未覆盖视图层原始输出，模板审阅为人工抽样（订单页、邮件模板）。已注意到 `resources/views/email/mail.blade.php:1` 的 `{!! $body !!}` 与买家输入 HTML 注入的可能性，但未纳入本次确认发现（需独立验证买家输入到该模板的完整链路）。
- **`cve.circl.lu` 返回空行**，其 CPE 供应商/产品匹配较粗，**空结果不构成“不存在”的证据**。
- **数据库层约束未被穷尽枚举**：仅检查了确认发现涉及的 `orders`/`carmis`/`coupons`/`goods`/`pays`/`admin_users` 表结构。
- **Revenue/业务规则审计未覆盖全部渠道**：9 个支付控制器中，Pin 了 yipay/vpay/stripe/payjs/mapay/paysapi/epusdt/tokenpay/coinbase 的签名与金额路径，但未对每个渠道的退款、部分支付、币种换算做端到端业务规则建模。
- **未验证运行镜像中的有效 PHP-FPM `listen` 地址**（初筛曾标记 `9000:9000` 暴露疑点，`PQ-10-R1` 已基于构建路径证伪，但未在构建后的容器内实测）。

### 6.4 结论的时效性

所有依赖与 CVE 结论为**时点快照**（2026-10-24）。此后发布的 advisory 对本报告不可见。**建议在 CI 的每次构建中执行 `composer audit --locked`**，并在发布流水线中补齐 SAST 与镜像扫描。
