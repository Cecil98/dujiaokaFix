## 1. 结论摘要

本次审计覆盖框架、依赖、路由与鉴权、危险函数 sink、安全配置、支付与业务逻辑、并发、上传与供应链。**未发现未认证 RCE，也未发现已知 CVE 命中的依赖版本**。风险集中在四类：

1. **支付信任链（高危）**：易支付回调的签名密钥来自 `install.sql` 内的公开占位字面量，且装完默认只启用该渠道，匿名者可离线算出签名完成订单并取走卡密（**PQ-001**）；Stripe `/check` 把「期望金额」与「订单绑定令牌」都交还客户端决定，小额 Source 可完成高价订单（**PQ-004**），而 `check`/`charge` 还是匿名 GET、省略 `context` 即无绑定（**PQ-004-GET**）。
2. **数据暴露（高危）**：匿名按邮箱检索订单没有归属证明，`search_pwd` 默认关闭，结果直接渲染已售卡密明文（**PQ-003**）。
3. **后台边界（中/低危）**：dcat 通用表单端点按请求指定类名实例化并调用，且 dcat-api 路由整体绕过 ACL、Form 授权恒真（**PQ-007**）；上传端点用客户端扩展名落盘且不校验授权（**PQ-007-UPLOAD**）；后台可写内容以 `{!! !!}` 原样输出到全站（**PQ-009**、**PQ-009-EXTRA-1**）。
4. **业务完整性与并发（中危）**：安装器仅以 `install.lock` 是否存在为闸门（**PQ-002**）、卡密分配与优惠券核销均为非加锁「先查后写」（**PQ-005**、**PQ-011**）、极验校验是恒 false 的死代码（**PQ-006**）。

> **方法学声明**：本报告所有结论为**源码级确认**。除依赖审计/版本核对为工具实测外，**未启动应用容器、未发送任何 HTTP 请求、未执行 PoC**。凡涉及运行时行为（Stripe 账户交互、并发统计、错误分支 oracle）的判定，均以源码路径 + 框架/数据库语义推导，并在条目中显式标注。

### 3.1 高危（4）

#### PQ-001 · 易支付回调使用出厂占位密钥，匿名可伪造通知零支付完成订单并取走卡密

- **位置**：`database/sql/install.sql:515`（种子密钥）→ `app/Http/Controllers/Pay/YipayController.php:82-101`
- **CWE**：CWE-798（占位/硬编码凭据）、CWE-345（验证不足）
- **可达性**：匿名 · GET `/pay/yipay/notify_url`　**置信度**：0.82
- **前置**：`install.lock` 存在；pays id 14/15/16 仍为占位 `merchant_pem`（出厂默认仅启用 `/pay/yipay`）；存在自动发货且有库存的商品

**链路**

1. `routes/common/pay.php:28` 注册匿名 GET 回调，组内唯一中间件 `dujiaoka.pay_gate_way` 为纯直通（`app/Http/Middleware/PayGateWay.php:17-20`）；GET 天然不受 CSRF 约束。
2. 签名 = `md5(排序参数串 . merchant_pem)`（`:94`），比较用 `hash_equals`（`:95`）——**算法与比较本身无缺陷**。
3. **缺陷在密钥来源**：`install.sql:515-517` 把 `merchant_pem` 写成仓内公开占位字面量；`:539-540` 先全量 `is_open=0` 再仅启用 `/pay/yipay`，因此全新安装唯一启用的正是可离线算签名的渠道。
4. `App\Casts\EncryptedOrPlaintext` 对非加密载荷原样返回，占位符直达签名器；安装器 `DB::unprepared` 导入种子，不触发加密写入分支。
5. 下单时 `payway` 仅校验为整数并直接作为 `pay_id`；金额校验只 `bccomp(actual_price, 传入值)`（同源），签名通过即 `completedOrder()` → `processAuto()` 发卡并把卡密写入 `orders.info`。

**修复**：出厂全部 `is_open=0` 且 `merchant_pem` 置空；启用前强制校验非空且不在占位符黑名单；回调绑定 `merchant_id/pid` + 一次性 nonce，并用网关服务端查询二次核账；下单校验 `pay_id` 已启用且已配置；对存量实例提供关闭占位密钥渠道的升级 SQL。

**验证器裁定偏差**：`high`（原报 `critical`）。“同一请求完成他人订单”子结论不成立（`order_sn` 为 16 位随机，不可枚举），已从影响中剔除。

#### PQ-003 · 匿名按邮箱检索订单缺少归属证明，直接返回已售卡密明文

- **位置**：`app/Service/OrderService.php:259`　**CWE**：CWE-639（IDOR）、CWE-200
- **可达性**：匿名 · `POST /search-order-by-email`、`GET /detail-order-sn/{orderSN}`　**置信度**：0.85
- **前置**：`install.lock` 存在；攻击者知道任一客户邮箱（`is_open_search_pwd` 默认未开启）

**链路**：路由位于 `web` 组，无 `auth`、无 `throttle`（`routes/common/web.php:24,30,32`；`app/Http/Kernel.php:33-43`）→ `withEmailAndPassword()` 只按 `email` 过滤，`when(!empty($searchPwd))` 使密码谓词可省略，无 session/cookie/owner 谓词（`:259-269`）→ 返回最近 5 单 → 模板原样输出 `orders.info`（`resources/views/unicorn/static_pages/orderinfo.blade.php:83-85`，默认主题；hyper:97-98、luna:112-127 同）→ 卡密明文泄露，且不存在的邮箱返回不同错误，构成邮箱存在性 oracle。

**修复**：用一次性限时签名邮件链接作为归属证明；`is_open_search_pwd` 默认开启并在开启时强制 `search_pwd` 非空 + 硬 `where()`（同时修正 `withEmailAndPassword` 对 `null` 的 TypeError）；检索/详情路由加 `throttle`；列表/检索视图不返回 `orders.info`；统一「未找到」响应。

**偏差**：原报「开关开启后空 `search_pwd` 可绕过谓词」被反驳（Laravel 12 `input()` 返回 `null` → TypeError/500，而非静默放行）；「泄露买家 IP」不成立（无视图渲染 `buy_ip`）；默认主题应为 unicorn。

#### PQ-004 · Stripe `/check` 以客户端提交的 `stripe_usd_amount` 作为期望金额，小额 Source 可完成高价订单

- **位置**：`app/Http/Controllers/Pay/StripeController.php:485`（漏洞块 485-515）　**CWE**：CWE-472、CWE-840
- **可达性**：匿名 · `GET /pay/stripe/check`　**置信度**：0.82
- **前置**：运营者启用 Stripe 渠道（pays id 21）并配置真实 `sk` 密钥（出厂 `is_open=0`，默认返回 `fail`）；攻击者自行创建 Source 并省略 `context`

**链路**：`$stripeUsdAmount = (int) $request->input('stripe_usd_amount', <服务端默认>)`（`:484-488`）→ 仅 `$request->filled('context')` 才校验订单上下文 HMAC（`:489-494`），省略即跳过绑定 → 把 Source 金额与**该攻击者值**比较（自指校验，`:501-508`）→ 以 Source 自身金额 `Charge::create`（`:509-513`）→ `completedOrder($data['orderid'], $cacheord->actual_price, ...)`（`:515`）。`OrderProcessService.php:418-422` 的 `bccomp` 比较的是同一订单价格，永远相等，无法发现少付。同文件 `:544-548`（`/charge`）与 `:454-459` 是正确写法（服务端计算金额），构成对照。

**修复**：期望金额只在服务端计算并丢弃请求值；订单上下文令牌改为**强制**（缺失即拒绝）；把实际扣款金额换算回订单币种传给 `completedOrder`，使 `bccomp` 成为真实对账；Source 增加服务端可控标识；支付路由加限流与幂等。

**偏差**：原报 `line: 524` 指向的恰是安全实现（`charge`），已修正为 `485`；`:454-459` 属另一条 CNY 路径，不是同一流程。

#### PQ-004-GET · Stripe `/charge`、`/check` 以匿名 GET 改变资金与订单状态，且回显原始异常文本

- **位置**：`app/Http/Controllers/Pay/StripeController.php:536`　**CWE**：CWE-352（无请求完整性）、CWE-209
- **可达性**：匿名 · `GET /pay/stripe/{check,charge}`　**置信度**：0.85
- **前置**：Stripe 已启用并配置真实密钥；攻击者知道目标 `order_sn`（可由 PQ-003 获取）；`/charge` 金额为服务端计算，故无价格绕过

**链路**：`routes/common/pay.php:37-38` 为 GET，`VerifyCsrfToken` 只保护非安全动词（`app/Http/Middleware/VerifyCsrfToken.php:19-24`），故无任何请求完整性控制 → 订单绑定 HMAC 被 `filled('context')` 包裹（`:536`），省略即无所有权绑定，第三方可用跨站 GET/`<img>` 驱动真实扣款与订单完成 → 异常分支 `return $e->getMessage()`（`:554-556`）向匿名调用者泄露内部支付诊断信息（Stripe 对密钥做掩码，无完整密钥泄露）。

**修复**：改 POST/签名 URL + CSRF；上下文令牌强制并绑定买家 session/`dujiaoka_orders`；pay 组统一 `throttle`；异常回显替换为通用错误 + 关联 ID 日志。

**偏差**：由 `medium` 上调为 `high`（未认证即可改变状态 + 绑定可选）；原报关于「Stripe 默认禁用」的前提有误（`install.sql:521` 该行 `is_open=1`，真正闸门是占位密钥）；「CSRF 借用买家凭据」表述较弱，实际缺陷是**未认证的可变状态 GET**。

#### PQ-007 · dcat 通用表单端点按请求指定类名实例化并调用 `handle()`，且 dcat-api 绕过 ACL、Form 授权恒真

- **位置**：`vendor/dcat/laravel-admin/src/Http/Controllers/HandleFormController.php:107`　**CWE**：CWE-470（不安全反射）、CWE-862（缺失授权）
- **可达性**：已认证后台会话（含无任何角色的受限管理员）　**置信度**：0.80

**链路**：`resolveForm()` 仅 `class_exists()` → `app($formClass)` → `method_exists('handle')`，无类型/白名单/命名空间校验（`:96-113`），随后 `sanitize($request->all())` + `handle($input)`（`:32-34`）。dcat-api 路由以 `config('admin.route.middleware')` 注册（`Admin.php:611-631`、`config/admin.php:68-77`），但 `Permission::isApiRoute()` 令其整体通过 ACL（`Permission.php:82-97`），且 `HasAuthorization::authorize()` 默认 `return true`、`app/` 内无覆写。可驱动 `SystemSetting`（覆写含 SMTP 口令/模板的系统配置）、`ImportCarmis`（任意卡密插入）、`EmailTest`，以及厂商 `InstallFromLocal`（按扩展包 `composer.json` 类名 `new $serviceProvider()`）。

**修复**：`is_subclass_of(Widgets\Form)` 类型闸门 + 显式白名单/不透明表单 ID；dcat-api 不得整体跳过 ACL，改为逐路由权限或在控制器内复查；为每个 `App\Admin\Forms\*` 覆写 `authorize()`；`InstallFromLocal` 仅超管可用或移除；保持扩展目录对 PHP 用户不可写；跟随上游修复。

**偏差**：由 `high` 下调为 `medium`。有效目标限于 Form 子类（任意类只会 500），出厂单超管部署无权限提升，RCE 分支受目录属主限制。

#### PQ-002 · 匿名 `POST /do-install` 仅以 `install.lock` 是否存在为闸门，可重写 `.env`、执行 DROP 建库脚本并重置 `admin_users` id=1

- **位置**：`app/Http/Controllers/Home/HomeController.php:202`　**CWE**：CWE-306
- **可达性**：匿名　**置信度**：0.72
- **前置**：`install.lock` 缺失且实例可网络访问（裸机/composer 部署、`INSTALL=true` 残留、宿主侧锁丢失）；攻击者提供**可达的 MySQL/Redis**（写入前连通性探测必须通过）；`.env` 可写

**链路**：`routes/common/web.php:37-42` 匿名组，唯一中间件 `InstallCheck` 仅 `file_exists(install.lock)`（`InstallCheck.php:19-24`）；CSRF 不构成屏障（`GET /install` 可取 token，`install.blade.php:700`）。`POST /do-install`：按请求参数重建 DB/Redis 连接并 `purge`（`:162-182`）→ 写 `.env`（`:202`）→ `DB::unprepared(install.sql)`（`:204`，含 21 条 `DROP TABLE`）→ 更新 `admin_users` id=1（`:206-211`）→ **最后**才写锁（`:216`）。

**修复**：增加一次性安装令牌（`hash_equals`）+ 回环/私网来源限制，或改为 CLI 安装命令；先原子写锁再变更 `.env`/结构；`.env` 用临时文件 + `rename` 并保留权限；目标库非空时拒绝执行 DROP；已初始化但缺锁时 fail closed。

**偏差**：由 `high` 下调为 `medium`。**「DROP 掉受害者全部数据 / 重置受害者管理员」被反驳**——连接在写入前已按攻击者参数重建，DROP 作用在攻击者自己的库上。真正后果是 `.env` 覆写 + `APP_KEY` 轮换导致的持久配置破坏/DoS，以及未安装实例的首访者抢占。

#### PQ-005 · 卡密分配为非加锁先读后写，并发完成订单可把同一张卡发给两个订单

- **位置**：`app/Service/CarmisService.php:31`　**CWE**：CWE-362
- **可达性**：匿名（支付回调 / 零价订单）　**置信度**：0.78
- **前置**：自动发货商品存在 `is_loop=0` 的未售卡密；≥2 笔待支付订单的回调被并发处理（notify 端点无限流）

**链路**：事务内普通 `SELECT ... take($byAmount)` 读取未售卡密（`:31-38`）→ 把明文写入订单并把状态置 COMPLETED、`save` → `UPDATE ... WHERE id IN (...) AND is_loop=0`（`:51`，**不限定 status=未售、不检查影响行数**）。MySQL 默认 REPEATABLE READ 下快照读使两个并发事务看到同一行；全仓库无 `lockForUpdate`/`Cache::lock`；`carmis` 无 `order_id`/唯一绑定。后果：同一张卡被两个订单交付，`sales_volume` 重复累加、通知重复派发。

**修复**：原子认领 `UPDATE ... WHERE goods_id=? AND status=1 AND is_loop=0 ORDER BY id LIMIT n` 后按批次回读并断言数量；或事务内 `lockForUpdate` + 影响行数断言；新增 `carmis.order_id`（唯一）与 `orders.trade_no` 唯一索引；`completedOrder` 加锁；`salesVolumeIncr` 仅成功分支执行；修正无卡密时 `count(null)` 在 PHP 8 抛 TypeError。

**偏差**：静态链路确认但**无并发实测**（MODE=static）；攻击者多为自伤式重复发卡，真实损失落在后续买家。与既有 `docs/security-audit/findings.json` 的 `PQ-06-B` 同源，应合并。

#### PQ-006 · 下单极验校验是死代码（Validator 对象当布尔），开启极验也无法阻止自动化下单

- **位置**：`app/Service/OrderService.php:81`　**CWE**：CWE-754（校验无效）、CWE-799（交互频率失控）
- **可达性**：匿名 · `POST /create-order`　**置信度**：0.90

#### PQ-011 · 优惠券核销为非原子先查后减且无下限，`is_use` 从未作为约束，可并发超发

- **位置**：`app/Service/CouponService.php:62`　**CWE**：CWE-362、CWE-840
- **可达性**：匿名 · `POST /create-order`　**置信度**：0.78

## 6. 覆盖缺口（Coverage Gaps）

**明确声明**：

1. **动态阶段未执行**：`MODE=static`。未启动应用容器、**未发送任何 HTTP 请求**、未执行 POC/Exploit。所有「可达/可利用」结论为源码路径 + 框架/数据库语义推导。
2. **未运行外部扫描器**：无 DAST（ZAP、nuclei、Burp 自动化）、无商业/第三方 SAST（Semgrep、Psalm、PHPStan 安全规则集、SonarQube）。仅使用仓库自带 AST sink 扫描器 + 人工验证，**sink 覆盖 ≠ 缺陷覆盖**（业务逻辑类缺陷不在 AST 规则内）。
3. **无运行时/并发实测**：PQ-005（卡密竞态）、PQ-011（优惠券超发）、PQ-006（自动化滥用）均无并发压测或统计数据；判定为「已确认代码路径」而非「已复现漏洞」。
4. **执行环境限制**：主机无 `php`/`composer`，所有 PHP 工具在 Docker 内只读挂载执行；结果依赖镜像与本地 `vendor/`，**与出厂 `--no-dev` 构建产物可能存在差异**。
5. **依赖侧仅版本匹配**：无 reachability 分析；`cve.circl.lu` 对控制用例也返回 0，未贡献结果；**npm/前端依赖（package.json、webpack.mix.js）未扫描**；**基础镜像 OS 包（webdevops/php-nginx:8.3、alpine:3.20）未做 CVE 扫描**。
6. **未验证 TLS/代理拓扑**：`TRUSTED_PROXIES`、真实反代链、HSTS 与 `isSecure()` 行为为静态推导（PQ-010）。
7. **支付渠道未联调**：Stripe、易支付、V免签、Payjs 等未做真实账户交互；签名算法与 SDK 内部实现仅读源码（如 Payjs SDK 内部签名未展开）。
8. **后台账号假定「受信但可审计」**：未做多管理员角色组合的权限矩阵实测；PQ-007、PQ-009 的权限提升前提依赖非默认多角色部署。
9. **未读取任何敏感值**：`.env` 值、Cookie、数据库口令、真实支付凭据均未读取或记录；占位字面量仅作源码文本引用。
10. **时效性**：结论为 2026-10-24 对提交 `b9ef09f` 的快照；发布前须重跑依赖与配置检查（基础镜像摘要与 advisory 库会变化）。

## 7. 修复优先级建议

| 优先级 | 项目 | 理由 |
| --- | --- | --- |
| **P0（发布前必须）** | PQ-001、PQ-003、PQ-004、PQ-004-GET | 可导致真实资金损失或卡密库存泄露，且均为匿名可达 |
| **P0** | PQ-007 | 后台边界内的授权绕过，若存在多角色部署即可提权（并可能扩展为 RCE） |
| **P1（尽快）** | PQ-002、PQ-005、PQ-006、PQ-011 | 安装器暴露、并发超发、反自动化失效，均为「条件满足即造成实质损失」 |
| **P2（下一迭代）** | PQ-007-UPLOAD、PQ-008、PQ-009、PQ-009-EXTRA-1、PQ-010 | 加固类：输入校验、输出编码、Cookie 属性、CSP |
| **持续** | 依赖与镜像 | 固定镜像 digest、替换 `box/spout`、审计 dcat fork、接入 SCA/镜像扫描 |

**建议的统一修复基线**

1. 支付：所有回调/返回端点「强制签名 + 强制服务端金额核对 + 强制非占位凭据」；`pay` 路由组统一加 `throttle`；渠道出厂全部关闭。
2. 订单：订单读取一律带归属能力（签名链接或 `order_sn` 能力），列表视图不返回卡密；检索端点限流并统一错误文案。
3. 后台：dcat-api 不再整体跳过 ACL；Form 增加类型闸门与显式授权；上传服务端校验 MIME/扩展名并限制字段。
4. 并发：卡密与优惠券改为条件 UPDATE + 影响行数断言，补唯一约束。
5. 部署：`.env.example` 默认 Secure Cookie、镜像固定 digest、删除 9000 映射、下发 CSP/HSTS。
